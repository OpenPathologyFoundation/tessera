## 0. Verdict

The calculation engine is the strongest part of this project and it is genuinely good. The denominator policy, the Wilson interval choice, the largest-remainder rounding and the method-provenance statement are all correct, well-reasoned, and better than what most commercial hematology middleware does. The reasoning recorded in `wbc-core.js` comments and in `REF-001` would survive a hostile clinical review.

Three things undercut it.

First, five defects in the *input* path — the keyboard handler and the absolute-count feature — are more likely to produce a wrong clinical number than anything the arithmetic could do. A held key silently inflates a count; four cell types in the right-hand preset cannot be un-counted at all; absolute counts are not corrected for NRBC even though the application's own reference document states the correction formula. The project has three selectable rounding methods and no `ev.repeat` check.

Second, the QMS documentation has drifted badly from the code. Nearly every counted quantity in `README.md`, `RTM-001` and `TR-001` is wrong; `SOP-001` instructs operators in a keyboard layout that no longer ships; `SDD-001` does not describe the implemented calculation at all. Most seriously, the archived test evidence records no commit hash, and the most recent "Approved" bundle was captured from a working tree that exists in no commit. In a Design History File that is the defect that matters, because it breaks the chain from a result to the code that produced it.

Third — and this is the answer to "is it overengineered" — yes, in configuration and process, not in the mathematics. The configuration schema is roughly four times larger than the clinical problem, and the excess has actively cost correctness: preset proliferation is why only one of eight profiles configures confidence intervals, and the 1,400-line visual editor is where the escaping bug and the dead branches live.

The good news is that the fix list is short and the expensive part — the reasoning — is already done.

## 1. P0 — Safety-relevant code defects

These five can produce a wrong number that reaches a clinical report. They are ordered by likelihood × consequence.

### P0-1 Key auto-repeat is not suppressed

`web/scripts/mdc-app.js` — `onKeyDown()` never checks `ev.repeat`. A held, sticky or bounced key adds cells at the OS auto-repeat rate, roughly 30/second, each with its own click sound. Nothing in the interface distinguishes this from deliberate counting, and at 200–500 cells a two-second stuck key is a plausible, undetectable, clinically material miscount.

The author already knows the flag: the theme shortcut at line 686 uses `if (ev.repeat) return;`. It was simply never applied to the counting path — the one place it matters.

```js
// in onKeyDown, immediately after the modifier check:

// A tally records deliberate acts. OS auto-repeat is not one: a held or
// bouncing key would add cells at ~30/s with no way for the operator to
// tell it apart from counting.
if (ev.repeat) return;
if (ev.isComposing) return;   // IME candidate windows emit key events too
```

**Traceability:** new SYS requirement under URS-021/022; new FMEA hazard (occurrence: moderate, detectability: very low).

### P0-2 Four cell types cannot be un-counted in the `right-hand` preset

`onKeyDown` resolves the key from the *character produced*: `var key = String(ev.key).toUpperCase();`. `web/settings/presets/right-hand.json` maps four categories to punctuation:

```json
".": "blasts",  ",": "meta",  "/": "baso",  ";": "mono"
```

On a US layout Shift+`.` produces `>`, Shift+`,` → `<`, Shift+`/` → `?`, Shift+`;` → `:`. None is in `outCodes`, so the handler returns before decrementing. **Blasts, metamyelocytes, basophils and monocytes cannot be corrected at all** — including blasts, the category most likely to be misidentified and most consequential when wrong. There is no error, no sound, no visual feedback; the operator sees the count simply not change.

Resolve `ev.key` first (so the printed layout wins for anyone on AZERTY or QWERTZ), then fall back to the physical key:

```js
var PHYSICAL_KEY = {
    Period: '.', Comma: ',', Slash: '/', Semicolon: ';', Quote: "'",
    BracketLeft: '[', BracketRight: ']', Minus: '-', Equal: '='
};
function physicalChar(code) {
    if (!code) return '';
    if (PHYSICAL_KEY[code]) return PHYSICAL_KEY[code];
    var m = /^Key([A-Z])$/.exec(code);
    if (m) return m[1];
    m = /^Digit([0-9])$/.exec(code);
    return m ? m[1] : '';
}

// in onKeyDown, replacing the single lookup:
var key = String(ev.key).toUpperCase();
if (!Object.prototype.hasOwnProperty.call(outCodes, key)) {
    // Shift changes the character punctuation keys emit (Shift+"." is ">"),
    // so undo would silently fail for any punctuation mapping. Fall back to
    // the physical key position, which Shift does not change.
    key = physicalChar(ev.code);
    if (!key || !Object.prototype.hasOwnProperty.call(outCodes, key)) return;
}
```

A regression test for every shipped preset — press and Shift-press every mapped key, assert the count returns to zero — would have caught this and would prevent the next one. That test does not exist today for any preset.

### P0-3 Absolute counts are not corrected for NRBC

This is the most substantive *scientific* gap in the application, and the project already knows the answer.

`web/calculation-reference.html` line 182 states the rule correctly:

> corrected WBC = uncorrected WBC × 100 ÷ (100 + NRBC per 100 WBC)

But `onWbcTotalInput()` in `mdc-app.js` does `Core.computeAbsolute(wbc, session.percentages[ct])` with whatever number the operator typed. The input is labelled only "Total WBC (×10⁹/L)". No correction is applied, no correction is offered, and nothing asks whether the entered value was corrected — even though the application is holding `nrbc_per100` at that moment.

Why it matters: NRBC resist lysis and are counted as leukocytes by impedance analysers, so the reported WBC is inflated whenever NRBC circulate. At 20 NRBC/100 WBC every absolute count derived from an uncorrected WBC is overstated by 20%. The absolute neutrophil count drives neutropenia grading and chemotherapy holds; a 20% overstatement moves values across the 1.5 and 0.5 ×10⁹/L thresholds. And the population where NRBC circulate — neonates, severe hemolysis, marrow infiltration — is exactly the population where the ANC decision is being made.

The application is one line away from being right and currently ships the failure mode its own documentation warns about.

```js
// Analysers count NRBC as leucocytes, so an uncorrected WBC overstates
// the leucocyte count whenever NRBC circulate, and every absolute count
// derived from it is overstated by the same factor.
function correctedWbc(wbc, nrbcPer100) {
    if (typeof nrbcPer100 !== 'number' || !isFinite(nrbcPer100) || nrbcPer100 <= 0) return wbc;
    return wbc * 100 / (100 + nrbcPer100);
}
```

Interface: relabel the field "Analyser WBC (×10⁹/L)", add a checkbox "already corrected for NRBC" defaulting to unchecked, and when NRBC > 0 display both the entered and corrected values with the factor. The method statement should record which was used. Do not silently correct — silently changing a number the operator typed is its own hazard.

### P0-4 `README.md` states a privacy property the code does not have

`README.md` line 389: "**No cookies** or localStorage are used for patient data."

`saveAutosaveState()` writes, on every keystroke, to `localStorage` under `wbcds_autosave`:

```js
caseNumber: state.caseNumber,
morphologyComments: el('morphComments') ? el('morphComments').value : '',
```

The accession number and free-text morphology comments therefore persist across browser restarts on the workstation. `USER-GUIDE.md` and `help.html` describe this honestly; only the README is wrong, and the README is the document a laboratory's privacy officer will read.

Autosave is a genuine safety feature and should stay. Three changes: correct the README; add an age limit so a stale autosave is discarded rather than resurrected (`if (Date.now() - Date.parse(data.timestamp) > 12*3600*1000) { localStorage.removeItem(AUTOSAVE_KEY); return null; }`); and record the residual data-at-rest exposure on a shared workstation as an FMEA entry with the training control that mitigates it. This is a HIPAA-relevant claim in a public README — it should be the first thing fixed, because it costs nothing.

### P0-5 `escHtml()` in the configuration editor does not escape quotes, and is used inside attributes

`web/scripts/config-editor.js`:

```js
function escHtml(str) {
    var div = document.createElement('div');
    div.textContent = String(str);
    return div.innerHTML;   // escapes & < > only — NOT " or '
}
```

It is then used in roughly twenty attribute positions, e.g. `value="' + escHtml(tpl.tplName) + '"`, and for `t.label`, `t.basis`, `f.label`, `f.basis`, `per.label`. A profile field containing a double quote breaks out of the attribute; `" onmouseover=…` executes. Two attributes interpolate raw values with no escaping at all.

The threat model is not idle. Profiles are JSON files shared between institutions and loaded from disk — that is a plausible delivery path, and it is the same reason `wbc-core.js` bothers with `sanitizeTemplateHtml`.

`wbc-core.js` already exports a correct `escapeAttr`, and `editor.html` already loads it. The fix is to delete `escHtml` and use `Core.escapeAttr` throughout. The counter side (`mdc-app.js`) is already clean — it uses `Core.escapeAttr` consistently.

## 2. Science review

I verified the substantive scientific claims against primary sources. Most hold. Four need correction and two are genuine gaps.

### 2.1 Verified correct

**The NRBC denominator policy is right, and it is the best decision in the codebase.** Excluding nucleated red cells from the peripheral blood differential denominator and reporting them per 100 WBC is the standard convention, and it is the form the corrected-WBC calculation requires. The bone marrow treatment is the opposite and also right: ICSH 2008 §2.6 places erythroblasts inside the nucleated differential count. Making this per-profile rather than global is correct — the two specimen types genuinely differ. `URS-030` states the rationale accurately, including the worked 66.7% → 60.0% example.

**The Wilson score interval is the correct choice and the published numbers are exact.** I re-derived the values quoted in `REF-001` §3.7 by executing the shipped engine: 40/200 gives 15.0–26.1%, 100/500 gives 16.7–23.7%, 0/200 gives 0.0–1.9%. All three match the document to the digit. The rejection of the Wald interval is correctly reasoned and correctly attributed to Brown, Cai & DasGupta (2001) — 2/200 does give a negative Wald lower bound.

**The M:E ratio formula matches ICSH 2008 §2.6 exactly**, including monocytes in the numerator, and the document correctly identifies that the alternative convention excluding monocytes is also in use and that the convention in force must therefore be visible in the report. That is a better-than-standard piece of design thinking.

**The Rümke citation is accurate** — *Blood Cells* 1985;11(1):137–140, and `REF-001` §3.8 correctly notes that the paper is about *ratios*, not single percentages, which makes the M:E display the affected element rather than the percentages. That is a subtle reading that most projects get wrong.

**The ICSH 2008 target-count rule is quoted correctly** (≥500 cells in ≥2 smears when a precise percentage is required; ≥300 when the count is not essential to diagnosis), and `REF-001` §3.3 correctly flags that `URS-105`'s "CAP recommendation" attribution for the 500-cell default was an error.

**The IEC 62304 Class A rationale in `DHF-001` §3.1 is defensible and unusually well argued.** It correctly invokes the allowance for risk control measures external to the software, names five of them explicitly, states the boundary conditions under which the classification would fail, and honestly says it "is not a claim that the software cannot produce a wrong number." That last sentence is worth more than most safety cases.

### 2.2 Corrections needed

**C-1 — "WHO 2022 withdrew it" is wrong; it was WHO 2016.** `wbc-core.js` in `computeSubsetPercentage`:

> "The governing case is 'blasts as a percentage of non-erythroid cells' — the pre-2022 WHO erythroleukaemia rule. WHO 2022 withdrew it in favour of counting blasts against all nucleated cells…"

The shift from the non-erythroid-cell denominator to all nucleated cells was made in the **2016 revision of the WHO 4th edition** (Arber et al., *Blood* 2016;127(20):2391–2405), which eliminated acute erythroleukemia, erythroid/myeloid subtype. WHO 2022 (5th ed.) and the ICC 2022 both retained the all-nucleated-cells denominator; neither made this change. Correct the comment, and correct `REF-001` [S6], which cites only the 2022 sources for a 2016 decision. Add Arber 2016 to the source register. The feature itself is correctly justified — labs do still report the historical figure for comparison — only the date is wrong.

**C-2 — The CLSI H20-A2 reference method is 400 cells, not 200, and the README conflates target with reference method.** `REF-001` §2.1 quotes it correctly via Hedley: "two reviewers counting 200 cells each." The 200-cell PB default is therefore *one observer's share* of the reference method, not the reference method. That is a perfectly good default — it is what routine practice does — but the DHF should say so plainly rather than let "200 per CLSI H20-A2" stand, which a reviewer will read as a conformance claim. `wbc-core.js` line 24 has the same shorthand.

**C-3 — Two decimal places on a 200-cell count is false precision.** `URS-032` requires percentages at 2 dp. A 200-cell count has a resolution of 0.5 percentage points; a 100-cell count, 1.0. Displaying 66.67% implies a precision of ±0.005% when the 95% interval is roughly ±6 points. The application computes and displays that interval, which makes the 2-dp figure next to it internally incongruous.

This is the one place where the science argues for *removing* configurability rather than adding it: derive the display resolution from the denominator instead of exposing `precision.display` as a knob. One decimal below 500 cells and one decimal at or above it is defensible; so is simply matching 1/n. Either is more honest than two fixed decimals and deletes a configuration field.

**C-4 — The 500-cell bone marrow default is unconditional where ICSH makes it conditional.** `REF-001` §5 already records this as an open gap, correctly. It is worth closing, because the fix is small and the current behaviour over-warns: a marrow examined for staging where the differential is not essential to the diagnosis gets a low-count advisory at 300 cells that ICSH would not require. Add a per-profile `targetCountBasis` variant, or a single "differential is essential to the diagnosis" toggle on the case screen that selects 500 vs 300 and records which was used in the method statement. The supporting evidence is already cited — Peterson et al., *Am J Clin Pathol* 2018 found 300-cell counts non-inferior across 165 cases with 100% sensitivity for AML at the 20% blast threshold.

### 2.3 Gaps worth closing

**G-1 — The corrected WBC.** Covered as P0-3 above. This is a science gap, not just a code gap: the application computes a per-100-WBC NRBC figure whose sole clinical purpose is to feed a correction it does not perform.

**G-2 — No interval on the M:E ratio, which is what Rümke actually warned about.** `REF-001` §3.8 identifies this precisely and defers it, showing an advisory instead. That is a reasonable interim position. If it is ever closed, the cheapest correct route is a parametric bootstrap over the multinomial counts rather than Fieller's theorem — about fifteen lines, no dependencies, and it handles the zero-erythroblast case gracefully where Fieller does not. Worth doing only if a clinical reviewer asks for it; the advisory is adequate.

**G-3 — A regulatory framing question that would simplify the whole project.** The DHF asserts 21 CFR Part 820, IEC 62304 and ISO 14971, and reasons carefully about software safety class. It never asks the prior question: **is this software a device at all?**

21 CFR 864.5220 (automated differential cell counter, Class II) covers devices that *identify* formed elements. This one explicitly does not — `DHF-001` §3 says so twice. And FDA's final Clinical Decision Support Software guidance (September 2022) sets out the four criteria under FD&C Act §520(o)(1)(E) for CDS that is not a device: it must not process a signal from an IVD or a signal acquisition system; it must display or analyze medical information; it must support recommendations to a health care professional; and it must let that professional independently review the basis for them.

This application appears to satisfy all four, and the fourth unusually strongly — the method statement, the confidence intervals and `calculation-reference.html` exist precisely so the pathologist can review the basis. The inputs are operator keystrokes, not analyser signals.

Adding a short §3.0 to `DHF-001` that walks the four criteria and concludes non-device status, with the IEC 62304 Class A analysis retained as a voluntary secondary position, is perhaps a day's work. It would be the single highest-leverage document in the file: it reframes the entire QMS as voluntary good practice rather than a compliance obligation the project is at risk of failing. That is also, directly, the answer to "am I overengineering this" — much of the DHF burden is self-imposed.

I am not a regulatory consultant and this is not regulatory advice; it is a reading of published FDA guidance that a qualified reviewer should confirm before you rely on it.

## 3. Documentation and QMS inconsistencies

### 3.1 The one that matters most

**Test evidence records no code identity.** `scripts/qms-run-tests.js` writes `environment.txt` containing date, node version, platform, arch, cwd and npm version. There is no `git rev-parse HEAD`, no branch, no dirty-tree flag and no source hashes.

This is not hypothetical. The tree at review time has ten modified files and two untracked ones, including `web/scripts/mdc-app.js` and a new `web/scripts/wbc-dialog.js`. The most recent evidence bundle — `2026-08-06_052733_counting-policy-editor`, referenced by an "Approved" `TR-001` — was therefore captured from code that exists in no commit, and nothing in the bundle records that. A DHF whose evidence cannot be tied to a code state does not do the one job a DHF has.

```js
// in scripts/qms-run-tests.js, environment capture:
const head  = sh('git rev-parse HEAD');
const dirty = sh('git status --porcelain');
lines.push(`git_commit: ${head}`);
lines.push(`git_branch: ${sh('git rev-parse --abbrev-ref HEAD')}`);
lines.push(`tree_state: ${dirty ? 'DIRTY' : 'clean'}`);
if (dirty) lines.push(`dirty_files:\n${dirty}`);
```

Refuse to run, or stamp the bundle `PROVISIONAL — DIRTY TREE`, when the tree is not clean. This is thirty minutes of work and it is the highest-value change in this entire review.

**Related:** `TR-001` headlines "851 tests passed across 3 verification layers and 3 browser engines" and states `Command: npm run test:all`, but its own machine-generated run log records `npm test`, and `qms-run-tests.js` contains no reference to Playwright at all. The `e2e-output-raw.txt` in the bundle is timestamped two minutes after the runner's own files — it was added by hand. The 266 browser results in the approved record have no auditable provenance. Make the runner execute and capture both layers.

**Also:** `npm test` cannot pass on a fresh clone. `tests/helpers/app-harness.js` reads `web/scripts/wbc-dialog.js`, which is untracked. A clone fails at module load with `ENOENT`, taking all 91 behaviour tests with it. Commit `web/scripts/wbc-dialog.js` and `tests-e2e/dialog.spec.js`.

### 3.3 Traceability gaps behind a 100% coverage claim

`RTM-001` §6.2 says "None" for URS requirements without SRS coverage and §8 claims 100%. In fact **URS-037, URS-038, URS-039 and URS-055** — confidence intervals, the near-threshold advisory, subset percentages, and the requirement to state the conventions — appear nowhere in RTM §5. These are the four safety-relevant requirements added by DCR-007/008/009, i.e. the newest and most clinically interesting ones.

Twelve hazards are untraced in §7: HA-012, HA-090 through HA-100. HA-092 (NRBC diluting the PB differential, pre-mitigation RPN 64) is among the highest-scored.

Sixty-one verification vector IDs cited by `RTM-001` and `TR-001` do not exist in `VV-001` — the whole `VV-SYS-*`, `VV-ABS-*`, `VV-LOW-*`, `VV-DEN-*`, `VV-CI-*`, `VV-THR-*`, `VV-SUB-*`, `VV-PROV-*` and `VV-RND-*` series. A traceability matrix that cites IDs which do not exist is worse than no matrix, because it produces the *appearance* of coverage. Either re-issue `VV-001`/`TP-001` against the ID scheme the tests actually use, or re-point RTM/TR at the test files and mark the old documents superseded.

### 3.4 Documents that would mislead an operator or a reviewer

**`SOP-001` is the serious one.** It is marked "Issued for local adoption" and documents a 9-category layout with `A`=blast, `S`=pro, `D`=gran, `F`=eryth; targets of 200 BM / 100 PB; a blocking warning dialog below minimum; and a table that locks after Count Done. The shipped profile is 14 categories with `A`=**mono**, `X`=blasts; targets 500/200; a non-blocking advisory; and URS-043 (locking) is withdrawn in favour of Continue Counting. **An operator following the issued SOP would press `A` for blasts and record monocytes.** This is the same defect class already recorded and closed as HA-097 for `USER-GUIDE.md`; it was not propagated. Fix this before anything else in section 3.

`TP-001` and `VV-001` carry the same stale key mapping (`TC-028`: "Press L (blasts=1)"; `L` is unmapped, `X` is blasts), as does `SDD-001` §3.8.

**`SDD-001` does not describe the implemented calculation.** §3.5.2 gives `percentage = (counts[cellType] / total) * 100 … toFixed(2)`. The shipped engine implements three selectable rounding policies with residual redistribution. The document contains zero occurrences of "Wilson", "confidence", "threshold", "denominatorExcludes" or "per100" — DCR-006 through DCR-010 are entirely undesigned. `RTM-001` cites SDD §3.9 through §3.17 and §5.1; the document ends at §3.8.

`SRS-001` **SYS-044** requires the percentage sum to be "100.00% +/- 0.10% (rounding tolerance)"; **SYS-231** requires exactly 100; `RA-001` §5.2.1 records that the ±0.10% tolerance was a control that never existed in the code. Likewise SYS-041 mandates exactly 2 decimal places while SYS-232 makes precision selectable 0–4.

`README.md` "Changing the Minimum Cell Count" documents a `minCellCount` field. No such field exists anywhere — it is `targetCount`, and `SRS-001` explicitly records that `minCellCount` was removed. The README also still says Tailwind and fonts load from CDN and lists air-gapped deployment as a limitation; `web/vendor/tailwind.js` is vendored and the service worker precaches it.

Version and status fields are incoherent across the file: `DHF-001` §5 lists SRS v2.7 / RA v2.8 / TR v3.1 against actual headers of 2.9 / 2.9 / 4.0, marks every document "Draft" while §7.2 and the documents themselves say "Approved", and its §7.4 counts eleven In-Review documents where there are fifteen. `TR-001` cites an evidence folder (`…_223522_…`) that does not exist and carries approval signatures dated the day *before* the run it reports.

### 3.5 Test suite honesty

`README.md`: "The governing rule is that **no layer verifies a copy of the implementation** — every test executes shipped code."

Measured across the suite: **191 of 524 test cases (36%)**, and **269 of 1,085 assertions (25%)**, are `assert.ok(sourceText.includes('…'))` against the app's own source files. Suites 03 (51/51), 06 (19/19), 07 (18/18) and 10 (37/40) are entirely or almost entirely of this kind. Representative:

```js
assert.ok(jsCode.includes('> 0'),        'Must have > 0 guard for decrement');
assert.ok(jsCode.includes('total === 0'), 'Must check total === 0');
assert.ok(jsCode.includes('--'),          'Must use decrement operator');
assert.ok(jsCode.includes('Copied!'));
```

Each would pass with the behaviour completely broken. The README's own table honestly labels those suites "Static" — it is the prose rule above the table that overclaims. Amend it to "every calculation, behaviour and system test executes shipped code; suites 03/04/06/07/10 are static structural checks," or convert 06/07/10 to jsdom, which would be a day's work and would retire the finding.

`config-editor.js` (1,417 lines) and `sw.js` (128 lines) are never executed by the layer that produces QMS evidence. Real coverage for them exists only in the Playwright layer, which the QMS runner never invokes (§3.1).

Suite 11 was **flaky under load** — 17 failures reproduced in 3 of ~10 runs, all dialog-dependent, all in `tests/11-application-behavior.test.js`. `tests/helpers/app-harness.js` uses a wall-clock `waitFor(…, 3000)` poll. Some of this may be interference from the tree being edited mid-run, but a QMS suite whose PASS depends on machine load is not a controlled measurement. Replace the poll with an explicit readiness promise published by `mdc-app.js`.

Yes — substantially, and concentrated in configuration and process rather than in the counting code.

| Shipped app (`web/`, excluding vendored Tailwind) | 9,298 |

The essential job — tally 14 keys, divide by a denominator, render a sentence — is 200–300 lines. That is roughly 30:1 for shipped code and 80:1 including tests and DHF.

Not all of it is waste. **`wbc-core.js` earns its 1,300 lines.** Wilson intervals, largest-remainder rounding, denominator exclusion and template sanitisation are non-obvious and genuinely clinical, and the comments explaining *why* are the most valuable prose in the repository. Do not cut there.

### 4.1 What to cut

**Presets: ten files, three profiles' worth of content.** Eight are reachable (`custom.json` is editor-only). Four of those eight are the identical 14-category panel differing only in key layout or M:E composition — `consensus-14`, `consensus-14-me-alt`, `frequency-ergo`, `right-hand`. Two more, `harmonized-9` and `legacy-9`, are the same ten categories reordered, and both are mislabelled "9-Part" while containing ten. Genuinely distinct: `minimal-5` and `body-fluid`.

Key layout and M:E convention are two *fields* inside a profile, not reasons to fork 180 lines of JSON. And the forking has already cost correctness twice: only `consensus-14` configures `thresholds` and `confidenceIntervals` (P0-9), and `right-hand` shipped with unusable undo on four categories because nobody pressed Shift+`.` (P0-2). Cut to three profiles — full marrow/blood, minimal PB screen, body fluid — and make layout a selectable field.

**Three rounding methods → one.** `wbc-core.js` spends 38 lines of comment explaining that `largest-count` "can displace one category by several points at integer precision" and is "a clinically misleading 1.9 point overstatement." Then it ships it as a selectable option. A laboratory can currently select a method the engine's own documentation calls misleading. Keep largest-remainder, keep `independent` only if a real customer demands it, delete `largest-count`. That removes a code path, a validation branch, a method-statement string, an editor control, and a test matrix.

**`confidenceIntervals.level` → fixed at 0.95.** Three Z-scores exist because a lookup table was easy. No laboratory will select 0.90.

**`precision.display` / `.report` → derive from the denominator.** See C-3; this is the scientifically better answer *and* it deletes two fields.

**`audio.*` and `handedness` → delete.** Every preset carries an `audio` object and the editor exposes an Audio checkbox that writes it. `AudioEngine.init()` reads only `sessionStorage`; `spec.audio` is never read by the counter. Turning audio off in a profile does nothing. `handedness` is editor-only metadata. Both are dead schema presented to users as working settings — worse than absent.

**`web/styles/counter.css`** (195 lines) is referenced by no page, and is the only thing referencing `web/fonts/Satisfy-Regular.ttf`, `images/retina_wood.png` and `images/brass.jpg`. `web/images/` also carries `puppies.jpg`, `ALL.jpg`, `wood-pattern.jpg`, `bone.png`, `grey_wash_wall.png` and three unused favicons. Delete them; they are shipped to every user.

**Dead code in the engine:** `calcPercentages` is exported, divides by the *wrong* denominator (`getTotal`, ignoring exclusions), is referenced by nothing in `web/` — and is verified by seven assertions in suite 01. That is false coverage on a function no user path reaches, and a loaded gun: wiring it into the UI would make the live percentages silently disagree with the report for any profile with `denominatorExcludes`. Delete it and its tests. `cellsForPrecision` is likewise test-only; keep it only if the near-threshold advisory will use it. `escapeAttr` is a verbatim alias of `escapeHtml` — harmless, but say so.

**The visual configuration editor (1,417 lines) is the single largest over-build.** It exists so a laboratory can, once, arrange 14 cell types into two rows and pick keys — then freeze that under change control. Against that: a 195-line JSON file and the validator that already exists in `wbc-core.js`. Both of the review's worst code-quality findings live in the editor (P0-5, P0-8); it can produce an invalid profile from a single click (P0-7); and it advertises four template placeholders when the engine supports thirteen plus `{{<cell>_per100}}` — so a lab building a PB profile in the editor cannot discover `{{nrbc_per100}}`, the one token that makes the denominator policy reportable.

If it stays, the honest reduction is to keep drag-and-drop layout and key capture — the two things JSON genuinely expresses badly — and replace the policy editor (roughly 380 lines) with a raw JSON textarea validated live by `WBCCore.validateConfig`, which already produces excellent error messages.

**Keep, despite the temptation to cut:** `denominatorExcludes` + `per100Reporting` (the best-justified feature here), `thresholds` + Wilson intervals (only one real use — blast % at 20/10/5 — but that use is worth the machinery), and the method-provenance statement (`buildMethodStatement`), which is what makes results comparable between laboratories and is rarer in this space than it should be.

### 4.2 Under-engineered, and it matters more

One line for `ev.repeat` prevents the most plausible route to a wrong count in the whole application, and it is absent while three rounding methods ship. Four categories in a shipped preset cannot be un-counted, in a project with 7,527 lines of tests. There is **no `aria-live` region on the count** anywhere — a keyboard-first tool whose entire interaction model is unlabelled keystrokes gives a screen-reader user no confirmation that a key registered. Two of three modals (`#preset-modal`, `#history-modal`) are hand-rolled with no `role`, no `aria-modal`, no focus move, no focus trap and no Escape, while `wbc-dialog.js` does all of that correctly right next to them. `CACHE_VERSION` in the service worker is a hand-edited string that git history shows has already been forgotten twice. And the low-count advisory appears only *after* finalisation, when the operator has left the counting screen — the one moment a prompt to continue counting would be useful is the moment before.

## 5. Improvement ideas

Ranked by value per unit of effort.

**High value, low cost.** Stamp the git commit and tree state into every evidence bundle (§3.1) — thirty minutes, and it is what makes the DHF mean anything. Generate the README/RTM count tables from the documents at release time — a ten-line script that ends an entire class of finding forever. Add `aria-live="polite"` to the grand total and the active cell's count, and route `#preset-modal` and `#history-modal` through the `WBCDialog` machinery that already exists. Derive `CACHE_VERSION` from a content hash at deploy time. Add the four-criteria CDS non-device analysis to `DHF-001` (§2.3 G-3) — a day's work that potentially reframes the compliance burden of the whole project.

**High value, moderate cost.** A per-preset keyboard round-trip test — press and Shift-press every mapped key in every shipped preset, assert every count returns to zero. Twenty lines, and it retires P0-2 and every future instance of it. Convert suites 06/07/10 from grep to jsdom so the README's headline claim becomes true. Move the low-count and near-threshold advisories *onto the counting screen*, live, so the operator sees "this count does not resolve the 20% threshold" while the slide is still under the objective — this is the feature the whole Wilson-interval apparatus was built for, and it currently fires after the useful moment has passed.

**Worth considering.** An operator-facing "what changed" note when a cached profile is superseded (`isCacheSuperseded` already computes it). Optional two-observer mode, deferred in URS §6 — this is the actual CLSI H20-A2 reference method and the only thing that would let the project claim conformance to it. A parametric bootstrap interval on the M:E ratio (§2.3 G-2), fifteen lines, only if a clinical reviewer asks.

**Explicitly do not build.** Anything that identifies cells. `DHF-001` §3.1.2 is right that it would remove risk control measure E2, void the Class A rationale, and move the software squarely inside 21 CFR 864.5220. That boundary is the most valuable line in the DHF; keep it.
